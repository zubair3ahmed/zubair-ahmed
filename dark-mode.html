01 / ContextWhere this started

A mature, light-only system — and a request to make it work in the dark.

Sedona is the design system behind a Nextiva-style contact-center workspace: live calls, tickets, contact directory, and the NextIQ AI assistant. It was already deployed in light mode, with a deep neutral scale and a single brilliant action blue. The library was healthy. What it didn't have was a second theme.

Sedona already had a 140-strong global palette, a semantic layer mapping colour to meaning, and a naming convention that aliased primitives → semantic tokens → component tokens. That existing discipline is exactly what made a second theme tractable — there was a clean seam to add modes behind.

02 / ProblemThe real challenge

Dark mode isn't an inverted palette. It's a second source of truth that has to mean the same thing.

The naïve version — flip the background, invert the text — breaks immediately. Shadows vanish, brand blue stops passing contrast, status colours glow, and the AI panel's carefully tuned "this is a suggestion, not a fact" cues fall apart. The problem was building a dark theme that was structurally identical to light so it could ride the same components, while being perceptually re-tuned so nothing lost its meaning.

The framing that unlocked it
Treat colour as a variable, never a value. If every component referenced a semantic token — surface, foreground, border, action — then a theme is just a second set of values behind those same names.
03 / ResearchWhy dark, why now

Two findings made dark mode a requirement, not a nicety.

Before touching a single token, I needed to know this was worth doing well. Two lines of evidence — one from our own users, one from the platform we were shipping into — turned dark mode from a backlog wish into a committed deliverable.

User behaviour

Most agents already live in dark mode.

Contact-center agents run long shifts, often in dimmed rooms, staring at a single workspace all day. When we looked at our base, the majority had set their operating system to a dark appearance by default — and our bright, light-only app was the one window forcing them back into glare. The demand for a dark theme wasn't speculative; it was the most consistent piece of qualitative feedback we had.

Majorityof users on a system-default dark appearance — fighting a light-only app all shift
Platform requirement

Microsoft Teams certification demanded theme parity.

We were publishing the Nextiva app inside the Microsoft Teams ecosystem. Teams apps must respect the host's appearance — Default, Dark, and High-contrast — and theme support is part of the store's design guidelines for certification. An app that stayed bright white inside a dark Teams window would feel broken and would not pass review. Dark mode stopped being optional the moment Teams became a distribution channel.

3 themesDefault · Dark · High-contrast — required to honour the Teams host appearance
Eye strain

Low-light rooms plus an all-day bright surface is a fatigue problem, not a preference. Dark mode reduces glare during long shifts.

Parity, not divergence

Teams certification wants the app to feel native in every host theme — same layout, same components, theme-aware colour.

Accessibility baked in

Both Teams guidelines and our own bar required WCAG AA. Contrast had to be designed in from the first token, not patched later.

04 / Key decisionsHow it was built

Four decisions turned one light system into two themes.

Each one started in Figma variables and ended up encoded in the same tokens engineering shipped. The goal throughout: one component definition, two modes behind it.

01
Semantic variables, not raw colours — with two modes.

Every component was re-pointed from primitive colours (blue/800, dark-grey/50) to semantic aliases — surface/primary, text/primary, border/primary, surface/action-primary. In Figma I added a Dark mode to the semantic and component-colour collections, so a single component instance renders correctly in either theme just by switching the mode. Engineering mirrored it one-to-one as a :root[data-theme="dark"] token block — the Figma variable names and the CSS custom properties are identical.

02
Elevation through layered surfaces, not shadows.

On white, hierarchy comes from soft midnight-blue shadows. On the dark canvas those shadows are invisible. So depth in dark mode is carried by the surface ladder above: surface/secondary sits deepest, surface/primary cards lift one step, surface/elevated pop-ups lift again. Borders do the rest — border/primary steps up to dark-grey/200 so a 1px hairline separates planes that shadow no longer can.

03
Swap the action blue — and flip the ink on top of it.

Sedona's primary #005FEC is gorgeous on white but fails AA as a fill on a dark surface. Rather than darken it, the system swaps the action surface to the brighter blue/300 — #49B6FF — and does the thing most dark themes miss: it flips the label to dark ink. text/on-action moves from white to dark-grey/800 #171C34, the inverse of light mode. White text on #49B6FF fails; dark ink on it clears AA comfortably. Status colours each lift one luminous step and their fills drop to low-alpha transparents so they read as state, not decoration.

04
Preserve meaning in the NextIQ AI panel.

The hardest surface was the AI assistant. In light mode, a "suggested action" reads as tentative through a soft grey fill and de-emphasised text; a superseded suggestion is struck through but still legible. Those signals are load-bearing — they tell an agent what's a fact versus a draft. In dark mode I rebuilt the same hierarchy with surface steps and opacity rather than grey-on-grey, so the panel keeps saying "this is a suggestion — verify before you speak it."

06 / ChallengesWhat was actually hard

The accessibility work lived in the edge cases.

Getting the obvious surfaces right was fast. The time went into the places where dark mode quietly breaks — translucency, glow, forced colours, and the things that are supposed to look faded but still need to be read.

Contrast on translucent tints
Status and primary tints are low-alpha fills, so their real colour depends on whatever surface sits behind them. A tint that passed on the page could fail on a raised card.
Fix: contrast was checked against every surface in the ladder, not just the page — tints were tuned to pass on the lightest surface they could land on.
Avatar colours blowing out
Light mode's friendly pastel avatars turned into glowing blobs on near-black, and the initials inside them dropped below readable contrast.
Fix: a parallel avatar ramp — deep saturated backgrounds with light, legible foregrounds — keeping each person's colour identity while passing AA on the initials.
"De-emphasised but still legible"
The NextIQ panel dims superseded suggestions. On dark, "dimmed" easily becomes "invisible" — but agents still need to read what was replaced.
Fix: dimming was capped at an opacity that still cleared the minimum contrast for text, so faded never meant unreadable.
Teams high-contrast mode
Beyond Default and Dark, Teams certification covers a forced high-contrast theme where the OS overrides colour entirely.
Fix: components were built to respect forced-colors — never relying on colour alone for state, so icons, borders, and labels still carry meaning when the palette is stripped.
A11YThe accessibility work, in evidence

Every colour pairing was measured, not eyeballed.

Each label, alert and surface pairing went through a contrast checker until it cleared WCAG AA. Where a colour couldn't pass at full strength, the trade-off was made in the variables — desaturating labels and dropping status fills to transparent tints rather than compromising legibility.

One library, two themes, zero forks — and it passed review.

For users

  • Less glare on long shifts. The workspace finally matches the dark appearance most agents already run all day.
  • Meaning preserved. AI suggestions, statuses, and call states read the same in either theme — no relearning.

For the platform

  • Teams-ready. The app honours Default, Dark, and High-contrast — clearing the design bar for store certification.
  • Native in any host. No more bright-white panel inside a dark Teams window.

For the system

  • Theming is now free. Future surfaces inherit dark mode automatically by using semantic tokens.
  • Design ↔ code parity. Figma variable modes and the code token block share one set of names.
The takeaway
Dark mode was never a colour exercise. It was proof that the system was built on meaning — and once colour is a variable, a new theme is a configuration, not a redesign.
